# 复评：提升工程包交付后的引擎水准（2026-09-05 二次评测）

> 评测对象：`D:\Thunder` 引擎源码
> 触发：完成 `audit/improvement-package/` 交付后
> 结论一句话：**引擎能力分未变（6.2 / 10），变的是"短板的可执行性"（就绪度 0 → 88%）。**

## 1. 先回答"升级完成了吗"

**没有。** 本轮对引擎源码**零改动**，实证如下：

```
find src -type f -newermt '2026-09-05 18:00'   ->  空
src/ 下所有 .cpp/.hpp 最后修改时间：2026-09-05 17:56（审计开始之前）
本轮新增内容全部落在 audit/improvement-package/（18:50–18:52）
```

因此任何能力维度（表达力、覆盖率、门禁、性能）的数值都不应上移。把规格、原型、
夹具、生成器当作"引擎升级"来庆祝是自欺——它们只是让升级变得可预测。

## 3. 真正变化的是"就绪度"

新增一个评测轴——**实施就绪度**：该短板是否已具备「可开工的方案 + 已验证的关键设计」。

评分口径：0 = 无方案；50 = 有规格；75 = 有规格 + 接口/落点；100 = 有规格 + 可运行验证或零风险决策。

| 维度 | 能力分 | 就绪度 | 依据 |
|---|---|---|---|
| 文本格式层 | 3 | **100** | 原型已编译运行：`ROUNDTRIP_OK`（数组/运算符/日期/引号/回写） |
| 脚本语言表现力 | 3 | 85 | 规格 02 含 `limit` 冲突解法、控制流 IR、确定性预算 |
| 对象与数据模型 | 7 | 90 | 含"不改 StrongId"的审慎决策（避免破坏存档/确定性） |
| 数值与确定性 | 7 | 85 | 双轨收敛点定在值求值器一处 |
| 模拟域深度与广度 | 4 | 75 | scope 手册 + AI/战争归属决策 |
| 工具链与编辑器 | 5 | 80 | 编辑器降级为 preview 的决策 + bootstrap 脚本方案 |
| 测试与质量门禁 | 7 | 90 | CI/bench/test 统一均有可执行规格 |
| 其余 10 项 | 5–9 | 80–100 | 均有规格与验收清单 |
| **平均** | **6.2** | **88** | |

就绪度 100 只有一项（格式层），因为它有**跑过的代码**——这正是原型的价值：把
"最不确定的那一步"变成已验证事实，避免 M1 开工时才发现语法设计不成立。

## 5. 提分杠杆分析（先做哪个最划算）

单点提分贡献（分数增量 × 维度权重）：

1. **格式层 3→7**：贡献最大，且**唯一有已跑通原型**、依赖最少。
2. **脚本语言 3→6**：贡献次大，但依赖 M1 完成（比较运算符进入 AST 后才能走到语义层）。
3. **值系统**：M3 后并入评分，是"从无到有"的增量，杠杆高但需先有 M1/M2。
4. **CI Vulkan（P2-1）**：分数增量小（6→7），但**零依赖、1 人周、消除 37% 代码零门禁的风险**——
   属于"最便宜的确定性改善"，可与 M1 并行插队。

**建议排期**：先花 1–2 周做 P2-3（修工具链）+ P2-1（CI Vulkan）——两者都是低风险、
立刻改善可信度的动作，且**M1 必须在工具链可用后开工**（否则无法验证 27 套件回归）。

## 6. 复评结论

- 引擎**仍是**"工程素质优秀、内容语言层未展开"的内核，6.2/10 未变。
- 与首次审计相比，**不确定性的总量下降**：5 项致命短板全部有了落地方案，其中
  最关键的语法设计已经用可运行代码证明可行。
- 两处审计结论已修正（clock checksum 已覆盖；StrongId 不塞 generation），避免了
  后续按错误前提施工。
- **下一步若只做一件事**：修复本机 cmake（P2-3）。它是所有后续验证的前置条件，
  也是当前唯一"不修就无法证明任何改进真实发生"的瓶颈。
